# Plan 8 — Two-Factor Authentication (TOTP) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add per-user TOTP two-factor authentication with a two-step login challenge, encrypted secrets, one-time recovery codes, re-authentication for enrollment and disablement, replay protection, and audit coverage.

**Architecture:** Extend the existing `users` table and `internal/auth` package with TOTP state, recovery-code rows, and short-lived MFA challenges. `BeginLogin` either issues a session (no 2FA) or an MFA challenge; `CompleteTOTPLogin` verifies TOTP or a recovery code and then creates the session. The dashboard gets an account-level `/account/security` page and a second login step.

**Tech Stack:** Go 1.26, PostgreSQL 16, goose, sqlc, existing `secretbox`, `pquerna/otp`, React 19, TanStack Router/Query, shadcn/ui, `qrcode.react`, Vitest/MSW, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-09-plan8-2fa-totp-design.md`

## Global Constraints

- Plan 8 scope only. No workspace enforcement, WebAuthn/passkeys, SMS/email OTP, trusted devices, admin reset, recovery-code expiry, 2FA for API keys, or SSO.
- TOTP: RFC 6238, HMAC-SHA1, 6 digits, 30-second period, 20-byte secret, issuer `o1 uptime`, account name = email.
- Accept current step and ±1 step; every successful TOTP verification advances `totp_last_used_step` atomically with `WHERE last IS NULL OR last < step`. Zero rows = replay.
- Active and pending TOTP secrets are sealed with `secretbox`; never stored plaintext, returned after enrollment, logged, or audited.
- Recovery codes: ten per generation, `XXXXX-XXXXX` Crockford base32 (50 bits), SHA-256 hashed, constant-time compared, single-use, returned only once.
- MFA challenges: 32 random bytes with `o1mfa_` prefix, SHA-256 hashed, 5-minute TTL, 5 attempts, single-use. The fifth wrong code returns 401 and consumes the challenge; later use returns 429. Failure increments commit before returning.
- Session cookies are set only after the second factor succeeds, or immediately for users without 2FA.
- Setup and enable require the account password. Disable and recovery regeneration require the password plus exactly one of TOTP code or recovery code. Both/neither is a 400 on the `factor` field.
- Enabling and disabling 2FA delete other sessions and keep the current session. Password reset deletes outstanding MFA challenges and clears pending setup.
- Login, login/TOTP, setup, enable, disable, and recovery regeneration all use the existing shared per-IP auth rate limiter. Other endpoints use `DisallowUnknownFields`.
- TOTP setup pending state expires after 10 minutes.
- API keys bypass TOTP. Users without 2FA, password reset, and existing sessions behave as before.
- Audit must never contain TOTP secrets, recovery codes, challenge tokens, passwords, or emails. `login_succeeded` records `method` (`password`, `totp`, `recovery_code`); `login_failed` adds `invalid_totp`/`invalid_recovery_code` and a known challenged user as actor.
- Account Security is at `/account/security`, linked from the UserMenu.
- UI copy is English. Every task ends with formatting, lint/typecheck where applicable, tests, and a commit.

## Review Focus

1. **Stolen session cannot enroll or weaken 2FA.** Setup/enable require the password; disable/regenerate require password + a second factor. A session alone must never attach or remove an authenticator or recovery codes.
2. **No session before the second factor.** Password login for a 2FA user returns a challenge and no `Set-Cookie`; expired, consumed, replayed, or over-attempted challenges never create a session.
3. **Secret and recovery containment.** The TOTP secret is ciphertext in the DB, recovery codes and challenge tokens are hashes, plaintext codes appear only in their creation response, and nothing leaks to logs, audit, URL, or later API responses.
4. **Replay and single-use.** A TOTP step cannot be reused across login/disable/regenerate; a recovery code works once and all old codes die on regeneration.
5. **Compatibility and cleanup.** Non-2FA login, API keys, password reset, and existing sessions keep working; enabling/disabling revokes other sessions; reset clears challenges and pending setup.
