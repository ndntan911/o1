Uptime and incident monitoring for small teams.

o1 watches HTTP endpoints for small teams: it probes on a schedule, opens and resolves incidents, notifies people over email, webhooks, Slack and Telegram, and publishes a public status page. It is a full product, not a demo of one — authentication, workspaces and roles, two-factor login, API keys, an audit trail, and a real deployment pipeline.

What it does

The product surface is deliberately complete: monitoring, incident workflow, delivery, public communication, and the accounts and permissions behind them.

  • Monitors and probes

    HTTP checks with method, headers, body, expected status, interval, timeout, and confirmation/recovery thresholds. Results land in monthly range partitions, and probes never follow redirects into private networks.

  • Incidents

    A monitor opens an incident after N consecutive failures and resolves it after N successes. Incidents can be acknowledged, stop reminders, and keep a timeline.

  • Alerts

    Email through Resend or authenticated SMTP, webhooks with optional HMAC-SHA256 signing, Slack incoming webhooks, and Telegram. Per-monitor switches, delivery history, and retries for transient errors.

  • Public status pages

    One page per workspace at /status/{slug} with 90 daily bars, uptime, and recent incidents. Monitor URLs, errors, and acknowledgement data never leak to it.

  • Teams and accounts

    Owner, admin, member, and viewer roles; workspace-scoped resources; TOTP two-factor with recovery codes; hashed API keys for scripts; and an admin audit trail that attributes actions to a user or an API key.

  • Incident insights

    On demand, an incident returns up to three ranked hypotheses, each citing a timeline event or field the server verifies before it is shown. The model never sees monitor URLs, headers, channel secrets, or recipients.

Four decisions worth reading

The interesting part is not the CRUD. It is the parts that are hard to get right.

  1. 01

    Probing untrusted URLs without becoming an SSRF proxy

    The guard resolves the host, rejects loopback, private, link-local, multicast, and cloud-metadata ranges, checks the scheme, port, userinfo, and fragment, then dials the IP it validated instead of the hostname. Redirects are limited and re-validated, and probes never send credentials to a new host. Alert destinations go through the same policy at save time and again before every send.

    probe/policy.go probe/probe.go alerts/config.go

  2. 02

    90 days of history that stays cheap to query and safe to delete

    Raw probe rows live in UTC monthly range partitions, while hourly aggregates back the status page and the 90-day uptime with up, min, max, and p95 latency. A partition drops only when it is wholly past the raw cutoff and hourly rollups cover it with matching counts; a mismatch re-rolls once and otherwise defers. Retention is a dry run by default, logs every candidate, and drops at most one partition per run.

    rollup/rollup.go retention/retention.go retention/prune.go

  3. 03

    Alerts that fail the way real providers fail

    The notifier classifies failures instead of retrying blindly: timeouts, 408, 425, 429, and 5xx are transient and retried up to five times with backoff; other 4xx and any 3xx are permanent and recorded as failed deliveries. Email sends carry an idempotency key so a lost response does not duplicate a message. Channel secrets are write-only, encrypted at rest with AES-GCM, and never appear in delivery history, logs, or error bodies.

    alerts/notifier.go email/resend.go

  4. 04

    Tenant isolation that is provable, and automation that is attributable

    Every query is scoped by workspace, and cross-tenant access returns 404 rather than 403 so a caller cannot probe what exists elsewhere. Roles are enforced at the handler boundary, and suspended workspaces keep reads while losing mutations and probes. API keys are shown once, stored as SHA-256 hashes with a public prefix, scoped to one workspace, rate limited per key, and never carry global admin rights. Every security-relevant action writes an audit event naming the workspace, the user, and the API key when one was used.

    apikeys/service.go audit/audit.go

Engineering practice

The deployment, the test gates, and the failure modes are part of the product, not an afterthought.

  • Tests are the gate. Unit and testcontainers integration tests run against real PostgreSQL. Playwright drives the deployed stack end to end, including 2FA, recovery codes, API key authorization, audit attribution, and accessibility checks.
  • CI is blocking. Five required jobs cover backend, integration, frontend, e2e, and pipeline checks (actionlint, shellcheck, Compose, and deploy scripts). Trivy scans the filesystem and both images before any push.
  • Releases are deliberate. Tags build linux/amd64 images, scan them, and publish by digest. Deploys are dispatched by hand, run from main for production, and rollback restores the previous release bundle.
  • The system is observable. Prometheus metrics on private listeners, OTLP tracing, Sentry with request data stripped, and a Grafana Alloy bundle that ships metrics and logs to Grafana Cloud.
